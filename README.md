# Microsoft 365 Copilot Readiness

A self-contained prototype for SharePoint and Teams governance, cleanup, and Microsoft 365 Copilot readiness.

For a literal pre-tenant preparation checklist, file inventory, and safe customer package instructions, begin with [START-HERE.md](START-HERE.md).

For complete synthetic users, roles, Teams, channels, SharePoint, and OneDrive scenarios in a disposable tenant, follow [TEST-TENANT-SEEDING.md](TEST-TENANT-SEEDING.md).

For hosting/licensing estimation and customer productization, see [docs/COST-AND-COMPONENTS.md](docs/COST-AND-COMPONENTS.md) and [docs/PUSH-BUTTON-READINESS.md](docs/PUSH-BUTTON-READINESS.md).

## Current implementation

Open the published site, then select an operational view:

- **Tenant governance** demonstrates the intended operational dashboard with clearly labeled sample data. It includes 30/60/90-day aging, owners, membership and guests, active-channel counts, SharePoint exposure indicators, RCD coverage, lifecycle status, filters, and workspace drill-down.
- **Program plan** summarizes completion, blockers, overdue work, ownership, phase health, and the Copilot rollout gate.
- **Program tasks** captures status, owner, target date, and notes for all 42 tasks across five phases.
- **Findings** combines current policy findings with their cases, evidence, case history, and role-gated next actions.
- **OneDrive** reviews personal-site metadata from a SharePoint admin export. Owners can optionally inspect a bounded sample of item names/permission metadata and revoke selected links/direct grants. File contents are never read; execution is guarded and dry-run by default.
- **My workspaces** includes owner renewal reviews, mover access reviews, and a second-approver dialog for delete requests.
- **Posture** includes approved baseline and drift-alert workflows as well as policy coverage, renewal state, and data-source health.

Disconnected views use clearly labeled sanitized sample fixtures. Tenant data and sample data are never merged. Sample actions do not persist. Live tenant operations remain limited to separately configured executor paths; lifecycle decisions, baseline approval, and case transitions record governance state and do not silently mutate tenant resources.

Program-task data is saved in the current browser. Use **Backup JSON** and **Restore JSON** to move or protect local state. **Export CSV** and **Print report** support program reporting.

## Shared Microsoft Lists sync

Task sync is optional. It synchronizes only the 42 program tasks through Microsoft Lists; it does not collect Teams, channel, membership, activity, SharePoint exposure, or RCD data. It requires a Microsoft Entra single-page application registration and access to a SharePoint site. See [CLOUD-SYNC-SETUP.md](CLOUD-SYNC-SETUP.md) for the one-time setup and required delegated permissions.

## Tenant connection

The backend includes a read-only GCC High data pipeline and normalized API. It runs under a backend service identity, not privileged browser JavaScript, and is designed to correlate:

- Microsoft 365 Groups, Teams, owners, members, and channel inventory from supported Microsoft Graph endpoints.
- Parent Team sites and the separate SharePoint sites used by private and shared channels.
- SharePoint administration and SharePoint Advanced Management/Data Access Governance findings.
- Restricted Content Discovery status and report data.
- A tenant-approved Team-level activity source with source and refresh timestamps.

Microsoft Graph's Teams team-activity report endpoint is not supported in GCC High. The activity connector must therefore be validated against a supported tenant report, an approved audit-derived aggregate, or a controlled report import before the dashboard can claim daily activity refresh.

The web page is served by an authenticated Azure Functions backend in a deployment; it is not browser-only. Member removal, selected sharing-link/direct-grant revocation, provisioning, and their guardrails have backend execution paths with a separate executor identity and dry-run default. Archive/delete require two-person approval and a separately enabled Executor confirmation; deletion is blocked without fresh clear hold/retention evidence. RCD remains read-only.

The collector now evaluates a versioned `workspace-health-v1` policy pack. It reports transparent ownership, activity-data, and exposure-data factors through `GET /api/workspaces`; stores explainable active and resolved records for `GET /api/findings`; and publishes policy intent through `GET /api/policies`. Missing activity or exposure data is `unknown`, never healthy. An ownership violation has a stable finding ID and creates one internal `detected`, dry-run governance case without overwriting subsequent case progress.

The backend stores cases, actions, exceptions, approvals, verification records, and audit records in Azure Tables. The Findings tab combines `GET /api/findings` and `GET /api/cases`, displays evidence and case audit history, and offers only transitions the signed-in app role can perform. The API still rechecks role, allowed transition, and ETag; case transitions change governance state, not Microsoft 365 permissions.

**Role changes are mover reviews.** The collector reads `ROLE_CHANGE_FEED_JSON` (`userId`, optional `userDisplayName`, `before`, `after`, optional `currentEntitlements` and `allowedResourceIds`; a test pathway, not an HR integration) and creates one access-review task per person, assigned to their new manager, or to the governance queue when none is known. The person's Teams are read from Microsoft Graph; only if that fails are the feed's entitlements used, and the review says so. The manager decides keep (with a reason) or remove for every Team (`POST /api/owner/tasks/{id}/mover-decision`). A removal is **not executed by the manager**: it becomes a pending request on that workspace's own review, and the workspace owner confirms it through the normal preview, confirm and verify path. Owners, and workspaces not yet in the inventory, are reported as not routed. A removal that already ran is never reopened.

Tenant-wide API reads require one of `Governance.Reader`, `Governance.Operator`, `Approver`, `Executor`, or `Auditor`. Case transitions are separated by duty: operators triage and assign, approvers approve or reject decisions and exceptions, and executors move approved work through execution and verification states. `Workspace.Owner` grants access only to the owner's own tasks and does not grant tenant-wide reads.

### Phase 1: owner workflow, risk and posture (read-only)

Owner decisions are records. Approved archive/delete decisions can proceed to a separate Executor action only when `ENABLE_LIFECYCLE_EXECUTION=true`; dry run remains the default and live mode still requires explicit tenant enablement.

- **Owner tasks.** The collector creates one renewal task per workspace (`ownertasks` table), assigned to its owners, or to the governance queue when there are none. `GET /api/owner/tasks` returns the signed-in owner's tasks (owners are matched on their Entra object id); governance roles can add `?scope=all`. `PUT /api/owner/tasks/{id}/steps/{step}` saves the five ordered steps (contacts, membership, permissions, links, metadata) with optimistic concurrency, so a wizard resumes where it stopped. `POST /api/owner/tasks/{id}/decision` records keep, archive, delete or "I am not responsible".
- **Reassignment and escalation.** "Not responsible" reassigns to the owner's manager, then the governance queue, and every step is recorded. Unanswered tasks escalate at 0, 7 and 14 days overdue (reminder, manager, governance queue). The safe default is always no change; non-response never archives or deletes.
- **Notifications.** `NOTIFICATION_MODE` is `off`, `dry-run` (the default: each message is recorded as simulated, nothing is sent) or `live`. Recipients come only from directory data (workspace owners, their managers, the mover's manager) and `NOTIFY_OPERATOR_EMAIL`; messages are fixed plain-text templates with a link and the workspace name, nothing else. Each message is sent once (a dedupe record per task, event and person), failures retry up to 3 times, at most 200 per run, and tasks older than 7 days do not announce themselves, so switching it on does not send a backlog. Live mode sends as `NOTIFY_SENDER` with the executor identity, which needs `Mail.Send`. Grant it only with `-NotificationMode live -NotificationSender <mailbox>`, then restrict it to that mailbox with an Exchange Online application access policy, because `Mail.Send` otherwise allows sending as any mailbox. `GET /api/notifications` (governance roles) lists delivery history with names, never addresses. A person with no email in the directory is recorded as skipped. **Live delivery has not been exercised against a tenant.**
- **Lifecycle gates.** Archive and delete need a reason and a different second Approver (`POST /api/decisions/{id}/review`). Delete additionally needs fresh evidence that legal hold and retention are explicitly clear. There is no automatic Purview hold connector. A separate Executor action requires the exact workspace-specific confirmation phrase. Archive is verified by reading `isArchived`; deletion is verified as a Microsoft 365 group soft-delete (404), not a content purge. Dry run records simulation; live execution requires `ENABLE_LIFECYCLE_EXECUTION=true`, `EXECUTION_MODE=live`, executor identity and required Graph permissions. Inconclusive Graph responses are marked execution-uncertain and cannot be blindly retried.
- **Decision register.** `GET /api/decisions` lists who decided what, when, on what evidence, and the outcome. Each decision links to an audit record keyed by the task id.
- **Risk.** Model `risk-v1` scores owners, exposure, guests, shadow users, sensitivity label and high-risk objects. Every input is returned with the result. An unknown input adds no points and a workspace with any unknown input can never be rated Low.
- **Evidence feed (sources with no Graph API).** Exposure, high-risk objects, legal hold, retention, site permissions, SharePoint activity, agents, and OneDrive admin metadata can be included in `feeds/evidence.json` (the collector identity has read-only access). Build it with `scripts/Export-WorkspaceEvidence.ps1`, which reads RCD and last content change, can optionally export provisioned OneDrive personal-site metadata with `-IncludeOneDrive`, and merges administrator overrides for facts from Data Access Governance, Purview, and permission reports. The OneDrive export contains no document names, contents, or item permissions. The collector validates the feed, records provenance, and ignores stale evidence after `EVIDENCE_MAX_AGE_HOURS` (72). Leave a fact out unless verified: legal-hold and retention false values are what let a delete request reach an Approver; Unknown keeps it blocked. SharePoint content activity is not Teams activity.
- **Shadow users.** Graph has no direct site-permission source. Supply `sitePrincipals` per workspace in the evidence feed, or `SITE_PRINCIPALS_FEED_JSON` for a small pilot. Workspaces without an entry show shadow users as Unknown, not zero.
- **Posture and scan transparency.** `GET /api/posture` returns policy coverage (evaluated against discovered workspaces), open and fixed violations, the rules with the most violations, and risk by workspace. `GET /api/sources` returns the last run of each source (`graph-teams`, `policy-evaluation`, `owner-tasks`, and any feeds) with status, age, record count and warnings; a source older than `STALE_SOURCE_HOURS` is flagged stale.
- **Graph permission.** Manager lookup needs `User.Read.All` for the collector identity. Set `RESOLVE_OWNER_MANAGERS=false` to skip it, in which case reassignment goes straight to the governance queue.
- **Native controls still to configure.** B3 (recurring renewal), C1 and C4 (ownerless detection and minimum owners) are native features, not built here. Configure Entra group expiration and the SharePoint Advanced Management ownership policy in simulation mode, then compare the results with the dashboard. The Posture tab shows each workspace's last renewal and expiration date as Microsoft 365 reports them; a workspace with no date has no expiration policy and is not treated as renewed.
- **Approved baselines (H3).** `GET /api/baselines` returns the active approved baselines and alert queue. An Approver previews a current workspace state (`POST /api/baselines/preview`) then records a reasoned, versioned baseline (`PUT /api/baselines/{workspaceId}`). The collector compares later snapshots to it and writes deduplicated drift alerts; Unknown facts never resolve an alert. Operators can acknowledge an alert; acknowledgement does not reset the baseline. New open alerts can be sent to `NOTIFY_OPERATOR_EMAIL` via the same notification mode, with one deduped message per alert cycle. No tenant setting is automatically reverted.

### Phase 2 (first slice): owner-executed member removal

An owner can pick members or guests in the review wizard, preview the removal and confirm it. Guardrails live in `backend/src/lib/execution.js`, not the page: only current non-owner members can be targeted, owners are never removed, nobody can remove themselves, at most 10 people per request, and membership is re-read from Microsoft Graph before and after, so "verified" means Graph confirmed it.

- **Dry run is the default.** Confirming records what would be removed (`simulated`) and changes nothing. `EXECUTION_MODE=live` additionally needs the separate **executor identity** (`enableExecution` in the template, `-EnableExecution` in the installer). The collector identity stays read-only, and the default Graph client has no delete method.
- **Executor permission.** The installer grants only `GroupMember.ReadWrite.All` to the executor identity, and only with `-EnableExecution`. It does nothing until you also set `-ExecutionMode live`.
- **History.** `GET /api/actions` lists every proposed and confirmed removal with its mode, result, who confirmed it and when. Each step also writes a verification and audit record keyed by the task.
- **Still limited:** no site-level shadow-access removal, no automatic guest deprovisioning, and no automatic rollback. OneDrive scans are bounded (100 items / 3 levels) and report when incomplete. Archive/delete live execution requires explicit opt-in, fresh evidence, two-person approval, typed confirmation, and live tenant verification.

### Phase 2 and 3 additions: trend, false positives, filters

- **Trend (G2).** The collector writes one posture point per day (`trend` table): workspaces, risk levels, exposure (with an Unknown bucket), guests, open violations. `GET /api/posture/history?days=90` returns the points and the change between the oldest and newest. A change is `null` when either end is Unknown, so missing data never reads as an improvement.
- **False-positive tags (D4).** `POST /api/suppressions` (role `Governance.Operator`) hides one policy violation on one workspace from the open counts. It needs a reason of at least 10 characters, a duration of 1 to 180 days (default 90), and an existing open violation. It expires by itself, can be revoked, never edits the finding, and is audited. The Posture tab lists each violation with its tag and reason.
- **Filters, saved views and export (D3).** The Posture risk table filters by name, risk level and guests, saves named views in the browser, and exports CSV. Cells that start with `=`, `+`, `-` or `@` are prefixed so a tenant-supplied workspace name cannot run as a spreadsheet formula.
- **Risk context (A5).** The review wizard shows the owner why the workspace is rated as it is, with every risk input and any Unknown inputs.
- **Risk definitions (D5).** `GET /api/risk/definition` returns the active weights, thresholds and minimum evidence. `PUT` needs the `Approver` role and a reason, validates the values (weights 0 to 50, at least three inputs above 0 so one fact cannot decide alone, minimum evidence 0.3 to 1), versions the change, audits it, and applies at the next collector run. `POST /api/risk/definition/preview` shows which workspaces would change level before anyone saves. The default definition reproduces risk-v1 exactly, and every score records the definition version it used.
- **Drift (H3).** Each collector run compares workspaces with the previous snapshot (`GET /api/changes?days=30`) and with an optional Approver-approved baseline (`GET /api/baselines`). Baseline changes open deduplicated alerts; new alert cycles can notify the configured governance mailbox. Acknowledging does not change the baseline. Unknown does not create a change and does not resolve an existing alert. Workspaces that appear or disappear are not reported.
- **OneDrive (G4, first safe slice).** The OneDrive tab reads a complete or pilot-scoped personal-site metadata export from `Get-SPOSite -IncludePersonalSite $true -Limit All`, supplied by `Export-WorkspaceEvidence.ps1 -IncludeOneDrive`. It shows owner, activity, storage, site state, and sharing capability, and records a reasoned review. The owner or a Governance.Operator can request a bounded scan (100 items, 3 folder levels) of item names and permissions (not file contents), then propose up to 10 link/direct-grant revocations with the standard dry-run/live and verify flow. The reviewer's own grant and owner access are never targeted; truncated scans are labeled. OneDrive scans require collector `Sites.Read.All` (`-EnableOneDriveSharingReview`); live revocation additionally needs the executor and `-EnableLinkRevocation`. Stale inventory disables actions.
- **Stale workspaces (G3).** A workspace with sourced activity older than `STALE_WORKSPACE_DAYS` (180) is stale. One with no activity source is Unknown, never stale.
- **Guest lifecycle (F3).** The collector captures up to 25 guest accounts per workspace; `GET /api/guests` merges them by person across workspaces with domains, the number of workspaces each guest is in, account age (from creation; sign-in activity is not collected) and whether they sit in a workspace with no owner. When a workspace has more guests than were listed, the inventory says so instead of showing a partial list as complete. Removal goes through the owner review, which re-checks membership first. `GUEST_REVIEW_DAYS` (180) sets the review age.
- **Copilot licences and adoption (H2).** `GET /api/copilot` returns seats purchased, assigned and available from the tenant's subscribed SKUs (only per-user Copilot seat SKUs count; Copilot Studio messages and credits do not), the licence holders, and 30-day adoption from the Copilot usage report. Active users come from the report; licence holders with no activity in the window, or missing from the report, are listed as idle seats, never-used first. The report is fetched as CSV from the stable path and, on a 404, from the preview path, because I could not confirm which one a given tenant or cloud serves. If the report cannot be read, adoption is Unknown while licence counts stay valid; if the tenant conceals user names in reports, activity cannot be matched to licence holders, so only a count of active users is shown. Names of idle holders are monitoring data about people: they are returned only to governance roles, and `COPILOT_SHOW_USERS=false` returns counts only.
- **Agent inventory (H1).** `GET /api/agents` merges two sources and labels each agent with its origin. Organisation-published Teams apps that contain a bot are read automatically from the Teams app catalog. Agents the tenant APIs do not list (Copilot Studio, Power Platform, Agent 365) come from the `agents` list in the evidence feed, which `Export-WorkspaceEvidence.ps1 -AgentsJson` includes. The inventory flags agents with no owner, with an owner that is unknown (the catalog does not provide owners, so those are "owner unknown", never "no owner"), not changed in `AGENT_STALE_DAYS` (180) days, and shared with everyone. A fact a source does not give is Unknown. A source that cannot be read keeps that source's previous agents instead of emptying the inventory. I did not add a connector for the Copilot package or Agent 365 preview APIs because I could not verify their shape or availability in GCC High; they can be added as another source once confirmed.
- **Enabling it.** `-IncludeCopilot` grants the collector `Organization.Read.All`, `Reports.Read.All` and `AppCatalog.Read.All` (read-only). Licence holders also need `User.Read.All`, which the installer already grants.
- **Sharing review and revocation (E-series, C3).** In the Team links step, and in the separate OneDrive review, an owner sees eligible links and direct grants in a bounded scan (up to 100 items and three levels, with truncation shown). OneDrive needs an admin metadata export and `-EnableOneDriveSharingReview` for collector `Sites.Read.All`; live execution additionally needs `-EnableExecution -EnableLinkRevocation`. The drive is resolved on the server; only links and direct grants are eligible; owner/inherited/group access and the reviewer's own access are protected; selected permissions are re-read before and after. Dry-run is default. Site-level shadow access still needs SharePoint administration.
- **Workspace metadata (F2).** Contacts and business purpose saved in the review update a per-workspace register (`GET /api/metadata`) and prefill the next review. A register write never blocks the owner from saving.
- **Provisioning for approved requests (A4 execution).** `POST /api/requests/{id}/provision` needs the `Executor` role; the approver cannot provision their own request. Dry run is the default. Live creation requires a verified tenant sensitivity-label mapping in `SENSITIVITY_LABEL_IDS`; an unmapped label fails before group creation. The label ID is included in the group-create request and read back before owners are confirmed. Verification failures retain the created group ID for manual reconciliation. Install with `-EnableSensitivityLabels -SensitivityLabelIdsJson <json>`. Graph label assignment availability and licensing must be validated in the customer tenant; if unsupported, provisioning fails closed.
- **Enabling execution.** `-EnableExecution` creates the separate executor identity. Add `-EnableProvisioning` for `Group.Create`, `Team.Create`, and `User.Read.All`; `-EnableLifecycleExecution` for `Group.ReadWrite.All` and `TeamSettings.ReadWrite.All`; and/or `-EnableLinkRevocation` for Sites permissions. `-EnableSensitivityLabels` requires the verified label map. OneDrive scanning needs `-EnableOneDriveSharingReview` for collector `Sites.Read.All`. These app permissions are tenant-wide; keep execution dry-run until an approved pilot validates scope. Lifecycle live actions additionally require `-ExecutionMode live` and the explicit feature flag.
- **Still limited:** OneDrive scan is bounded and reports truncation; it is not a complete tenant-wide file audit. Site-level shadow-access removal, automatic guest deprovisioning, automated rollback, and live tenant verification remain outstanding.
- **Self-service requests and catalog (A4, H4).** `GET /api/catalog` lists approved templates (project team, department, partner collaboration) with server-side guardrails. `POST /api/requests` submits; `POST /api/requests/{id}/decision` (Governance.Operator) approves/rejects and the requester cannot self-approve. Provisioning is a separate Executor route; dry-run is default. Live provisioning requires `SENSITIVITY_LABEL_IDS` to map the requested label to a verified tenant GUID, applies the group label, and reads it back. Unmapped labels fail before creation; uncertain label/owner readback leaves the created group ID for manual reconciliation. The label mapping and live Graph path still need tenant validation.

## Backend development

Copy `backend/local.settings.json.example` to the Functions local settings file and provide local-only values. `ALLOW_LOCAL_AUTH=true` permits unauthenticated access to GET routes for isolated development; it is `false` by default and must never be enabled in Azure. Case transitions do not honor this bypass and always require a principal with the appropriate app role.

From `backend`, run `npm test`. Most tests are unit tests. Two files, `store.emulator.test.js` and `handlers.emulator.test.js`, run the real storage layer and the real HTTP handlers (with the Easy Auth principal header) against the Azurite table emulator, which `npm install` provides as a dev dependency; they skip themselves if it cannot start. Handlers that call Microsoft Graph (member list, sharing scan, provisioning) are covered by library tests with a fake Graph, not end to end. `STORAGE_CONNECTION_STRING` points the storage layer at an emulator for local work and must never be set in Azure. Run `npm start` when Azure Functions Core Tools are available.

See [CUSTOMER-DEPLOYMENT.md](CUSTOMER-DEPLOYMENT.md) for the recommended Azure Government architecture, customer prerequisites, identity and permission model, pilot validation, and production installation sequence.

No tenant IDs, client IDs, access tokens, passwords, or SharePoint URLs are committed in this repository.
